MemPalace MCP single HTTP owner

Fixing writer-lock starvation across concurrent Claude Code sessions by replacing per-session stdio writers with one serialized HTTP owner.

Date 2026-07-12 Status deployed (temp) · systemd pending Host 10.0.17.205 mempalace 3.5.0
Decision

Run one persistent MemPalace MCP server in HTTP mode (mempalace-mcp --transport http --port 8765) and repoint every session's MCP client at http://127.0.0.1:8765/mcp. All writes funnel through one process; _HTTP_REQUEST_LOCK serializes them — one Chroma writer, no per-session lease to squat.

01Problem

Each concurrent session spawned its own stdio MCP server. Every server grabs a process-lifetime writer pre-lease (_acquire_mcp_writer_lock) on its first tool call — including the mandatory on-wake mempalace_status. The oldest session wins the lease and squats it while idle; the read-only verdict is latched with no retry, so every newer session is permanently read-only and its mutating tools fail with -32001 "Peer MCP writer active" until it restarts.

The single-writer guard is correct — ChromaDB PersistentClient is not process-safe; two processes writing one path corrupt the HNSW index. The defect is the topology: per-session writers competing for one lease. Full RCA: claude_docs/mempalace-writer-lock-rca-20260712.md.

Before — starvation

session A (idle)
session B (active)
session C (active)

After — one owner

session B
session C
all POST /mcp ↓
:8765 HTTP owner — serialized writer
per-op lock · one Chroma writer

02Why ALLOW_PEER_WRITER=1 is required and safe

Two facts, both confirmed from mempalace 3.5.0 source:

1 · The built-in HTTP mode alone breaks writes

_MCPHTTPServer is a ThreadingHTTPServer (mcp_server.py:4632) — one worker thread per request. The pre-lease grabbed on the first request's thread cannot be re-entered on a later write thread: mine_palace_lock's re-entrancy is keyed on threading.local() (palace.py:1043). The write attempts a fresh flock(LOCK_EX|LOCK_NB) on the same lock file, fails, and reports the palace "held by PID <self>". Reads work; writes self-deadlock.

Upstream

Reported as MemPalace/mempalace#1998. Fix belongs upstream: serve HTTP single-threaded, or make the pre-lease process-scoped. mempalace is third-party (READ-only for us).

2 · The flag disables only the redundant pre-lease

ALLOW_PEER_WRITER=1 skips the process-lifetime pre-lease — not the per-write mine_palace_lock. That per-op lock (LOCK_NB) still fires on every write and still blocks concurrent Chroma writes cross-process. For a single owner the flag is safe and sidesteps the thread-local self-conflict. (The RCA's earlier "re-opens corruption" dismissal assumed the flag disables all write locking — it does not.)

Verified

Two concurrent writes to the owner both returned success: true with distinct drawer IDs, no -32001, no self-conflict.

03Residual fragility

The pre-lease and the per-op mutex are the same file lock, so one process cannot both "hold the lease to block peers" and "acquire per-op as the owner." With the pre-lease disabled, the owner is authoritative only while no other mempalace writer runs against this palace. A lingering stdio session that does an on-wake status grabs the pre-lease and fail-fasts the owner's writes until it exits.

  • Steady state (all sessions on HTTP, zero stdio): correct and reliable.
  • Durable robustness needs the upstream fix (#1998). Until then: run no stdio mempalace servers against this palace.
  • A fork is the only in-house durable alternative; deferred unless the fragility bites.

04Runbook

Install / start (systemd system unit — needs sudo)

sudo cp deploy/mempalace-mcp-http.service /etc/systemd/system/mempalace-mcp-http.service
sudo systemctl daemon-reload
sudo systemctl enable --now mempalace-mcp-http.service

Verify writable

curl -s -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"mempalace_add_drawer","arguments":{"wing":"canary","room":"smoke","content":"live-check"}}}' \
  http://127.0.0.1:8765/mcp
# expect: "success": true, a drawer_id

Unstick (writes failing with "held by PID")

lslocks | grep mine_palace     # find the holder PID
ps -o pid,cmd -p <PID>         # confirm a stdio `python -m mempalace.mcp_server`
kill -TERM <PID>               # frees the flock; owner reacquires per-op next write
